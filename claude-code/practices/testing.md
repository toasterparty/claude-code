# Tests
- Write a test as documentation of behavior, to be read cold by someone who has not read the implementation
- Prefer a named example - one concrete input and its expected result, both visible in the test body - to a parametrized sweep over cases no reader can name
- Name a test for the behavior it pins, so a failure reads as a sentence describing what broke
- Assert the contract the interface declares through its signature, documentation, or docstrings, never a private attribute, an internal call order, or an intermediate value. This is the most common mistake
- Where the behavior worth asserting is not declared anywhere, declare it first, then assert it
- Assert the exact value wherever it is knowable, not merely `is not None`, a length, or a type
- Prose - error and log messages, help text - is not contract unless declared so. Assert the error's type, code, or structured fields, and pin wording only where the interface promises it
- The expected result is a literal, never recomputed by the code under test or by a reimplementation of it
- Deterministic: seed randomness, freeze time, no sleeps, no real network
- Mock only at boundaries the project does not own - the clock, the network, the filesystem
- Delete a test whose functional coverage another test already provides
- Refactor boilerplate into fixtures and helpers - never the input or the expected result, which stay in the test body
